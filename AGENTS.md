# Agent Instructions

These instructions apply to the whole repository.

## Product Goal

Build and maintain a Manifest V3 Chrome extension that turns the X timeline into an image-focused gallery while keeping user data local.

Current product assumptions:

- Gallery mode is toggled from the popup and defaults to off.
- Gallery mode targets X timeline pages on `x.com` and `twitter.com`.
- Post detail pages keep the widened layout and hidden sidebars, but should not hide normal post metadata or actions.
- The default gallery feed shows single-image posts that pass the current context filters.
- Videos, GIFs, multi-image posts, quote-source cards, reply-context posts, and non-image posts are hidden by default.
- Ads remain visible when they otherwise qualify, but the custom not-interested action is replaced with an `Ad` label.

## Code Organization

- Extension entrypoints live under `src/entrypoints/`.
- Shared code lives under `src/utils/`.
- Keep X timeline classification and layout logic in `src/utils/x-gallery.ts` unless a split clearly reduces complexity.
- Keep X route helpers in `src/utils/x-page.ts`.
- Use `src/utils/messaging.ts` for runtime message contracts.
- Use `src/utils/storage.ts` for persisted extension state.
- Do not put helper modules under `src/entrypoints/`; WXT treats that tree specially.

## Manifest V3 and Permissions

- The background script is a service worker. Do not rely on long-lived in-memory state.
- Persist extension state through `chrome.storage.local`.
- Keep host matches narrow. Do not add `<all_urls>` for X-specific work.
- Do not load remote JavaScript.
- Do not add permissions unless the feature requires them.
- If permissions are broadened, document the reason in the relevant PR or commit message and update `docs/chrome-web-store.md`.

## Public Repository Safety

This is a public repository. Before finishing work, check that no private or generated local data is being added.

Never commit:

- `.wxt/`
- `.output/`
- `tmp/`
- `.env`, `.env.*`, `.envrc`, `.direnv/`
- Chrome profile data, cookies, sessions, or local storage databases
- credentials, tokens, private keys, packaged CRX signing keys, or service account files
- ad hoc screenshots that include real X accounts, private timelines, or private posts

Allowed generated assets:

- `store-assets/*.png` may be committed only when generated by `corepack pnpm run store:assets` and containing mock UI only.
- `public/icon/*.png` may be committed as extension icon assets.

Keep public documentation accurate. Do not claim Chrome Web Store publication, external API behavior, data collection behavior, or privacy guarantees that the code does not support.

## X and Browser Testing

X may reject browser sessions launched by WXT/web-ext during login.

Use this flow for authenticated X development:

```sh
corepack pnpm dev:x
```

Then manually load `.output/chrome-mv3-dev` in normal Chrome from `chrome://extensions`.

For headless real-X inspection without taking over the user's Chrome window:

```sh
corepack pnpm auth:x:headless:reset
corepack pnpm inspect:x:headless:gallery
```

Only run the auth command when a login profile needs to be created or reset. Never automate X login and never commit Chrome profile data.

## Verification

Before finishing implementation work, run:

```sh
corepack pnpm run check
corepack pnpm run format:check
```

For X layout or selector changes, also run:

```sh
corepack pnpm inspect:x:headless:gallery
```

For Chrome Web Store submission work, run:

```sh
corepack pnpm run store:package
```

If a command cannot be run, report that clearly.

## Testing Expectations

- Add or update unit tests for selector, classifier, and layout-marker changes.
- Prefer fixture-style DOM tests for X markup behavior.
- Use live X inspection only for visual or behavior checks that cannot be represented reliably in unit tests.
- Do not perform actions on live X that materially change the user's account state unless explicitly requested.
